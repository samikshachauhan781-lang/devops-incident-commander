# Day 7 Changes Summary: Incident Timeline & Audit Trail

## Overview
This document summarizes the implementation of Day 7: Incident Timeline & Audit Trail for the DevOps Incident Commander project. This enhancement adds comprehensive audit logging and timeline functionality to track all incident lifecycle changes.

## What is an Audit Trail?
An audit trail is a chronological record of all significant changes made to incidents in the system. Every time an incident is created, updated, or deleted, a detailed event is logged that captures:
- What changed
- What the values were before and after the change
- When the change occurred
- Which incident was affected

This creates a complete historical record that DevOps engineers can use for:
- Understanding incident history
- Debugging issues
- Compliance and audit requirements
- Learning from past incidents

## Why DevOps Engineers Need Incident History
1. **Troubleshooting**: When an incident occurs, engineers need to understand what changed just before the problem appeared
2. **Decision Making**: Historical data helps teams make better decisions about incident response
3. **Learning**: Reviews of past incidents reveal patterns and best practices
4. **Accountability**: Clear audit trails show who made what changes and when
5. **Recovery**: Understanding the sequence of events helps in root cause analysis

## What an Event Record Contains
Each event record in the audit trail includes:

### Core Fields:
- **id**: Unique identifier for the event
- **incident_id**: The incident this event relates to
- **event_type**: What type of change occurred
- **description**: Human-readable explanation of the event
- **created_at**: When the event occurred (UTC timestamp)

### Optional Context:
- **old_values**: Previous state values (JSON format)
- **new_values**: New state values (JSON format)

### Example Event:
```json
{
  "id": "a860ed9b-b410-40ac-be0b-96b5e291179e",
  "incident_id": "3c240ff9-ee44-44ab-ba68-0a3ed92b9c06",
  "event_type": "incident_status_changed",
  "description": "Incident status changed from 'open' to 'resolved'",
  "old_values": {"status": "open", "severity": "high"},
  "new_values": {"status": "resolved", "severity": "high", "resolved_at": "2026-10-16T12:30:00.000Z"},
  "created_at": "2026-10-16T12:30:00.000Z"
}
```

## How the `incident_events` Table Relates to Incident Records

### Database Schema:
- **incidents table**: Stores current/active incident data
- **incident_events table**: Stores historical audit trail events

### Relationship:
- Each incident has its own set of events in the incident_events table
- Events persist even when incidents are deleted (preserving history)
- Events are linked to incidents via incident_id foreign key (no cascade deletion)

### Why Retain Events After Deletion:
1. **Historical Reference**: Deleted incidents may still need to be referenced
2. **Audit Compliance**: Regulatory requirements often mandate preserving deletion records
3. **Debugging**: Future issues may require understanding why an incident was deleted
4. **Learning**: Patterns in incident deletions can reveal systemic issues

## How Automatic Audit Logging Works

### Automatic Logging Implementation:
The audit trail is automatically generated by the application without requiring client intervention:

#### 1. Incident Creation (POST `/incidents`)
```python
# When creating an incident, automatically log:
event = IncidentEvent(
    incident_id=incident.id,
    event_type="incident_created",
    description=f"Incident created with title '{incident.title}'",
    old_values=None,
    new_values=incident_data_json
)
save_incident(incident, event)
```

#### 2. Incident Updates (PATCH `/incidents/{id}`)
```python
# When updating an incident, log changes:
if "status" in changed_fields:
    event_type = "incident_status_changed"
elif any_field_changed:
    event_type = "incident_updated"

event = IncidentEvent(
    incident_id=incident_id,
    event_type=event_type,
    description=f"Incident updated: {', '.join(changed_fields.keys())}",
    old_values=old_values_json,
    new_values=new_values_json
)
```

#### 3. Incident Resolution/Reopening
```python
# Special handling for status transitions to incident_resolved and incident_reopened:
if new_status == "resolved" and old_status != "resolved":
    event_type = "incident_resolved"
elif new_status != "resolved" and old_status == "resolved":
    event_type = "incident_reopened"
```

#### 4. Incident Deletion (DELETE `/incidents/{id}`)
```python
# Before deleting, log the deletion:
event = IncidentEvent(
    incident_id=incident_id,
    event_type="incident_deleted",
    description=f"Incident deleted: '{incident.title}' (Service: {incident.service})",
    old_values=incident_data_json,
    new_values=None
)
save_event(event)
# Then delete the incident
```

### Transactional Requirements:
- All database operations (incident + events) succeed or fail together
- If event logging fails, the incident operation is rolled back
- This ensures consistency between incidents and their audit trails

## Why Database Transactions Matter

### Critical for Audit Logging:
1. **Consistency**: Either both the incident and its audit event are saved, or neither
2. **Reliability**: Prevents situations where an incident exists without its audit trail
3. **Debugging**: Failed operations are easier to troubleshoot when transactions are atomic
4. **Compliance**: Regulatory requirements often mandate transactional integrity

### Implementation:
- Use SQLite's `BEGIN IMMEDIATE TRANSACTION` to lock the database
- All related operations are grouped within a single transaction
- On failure, `ROLLBACK` undoes all changes in the transaction
- On success, `COMMIT` persists all changes

## How the Timeline Endpoint Works

### API Endpoint: `GET /incidents/{incident_id}/timeline`

#### Query Parameters:
- `page`: Page number (default: 1)
- `page_size`: Events per page (default: 10, max: 100)
- `sort_by`: Field to sort by (id, incident_id, event_type, description, created_at)
- `order`: Sort direction (asc or desc)

#### Response Structure:
```json
{
  "incident_id": "3c240ff9-ee44-44ab-ba68-0a3ed92b9c06",
  "events": [
    {
      "id": "event-1",
      "incident_id": "3c240ff9-ee44-44ab-ba68-0a3ed92b9c06",
      "event_type": "incident_created",
      "description": "Incident created with title 'Database Issue'",
      "old_values": null,
      "new_values": {
        "title": "Database Issue",
        "severity": "critical",
        "status": "open",
        "service": "database-service"
      },
      "created_at": "2026-10-16T10:00:00.000Z"
    },
    {
      "id": "event-2",
      "incident_id": "3c240ff9-ee44-44ab-ba68-0a3ed92b9c06",
      "event_type": "incident_resolved",
      "description": "Incident resolved with status 'resolved'",
      "old_values": {"status": "open"},
      "new_values": {"status": "resolved", "resolved_at": "2026-10-16T12:00:00.000Z"},
      "created_at": "2026-10-16T12:00:00.000Z"
    }
  ],
  "total": 2,
  "page": 1,
  "page_size": 10
}
```

#### Response Codes:
- **200**: Incident exists and events are returned (empty list if no events)
- **404**: Incident doesn't exist (including deleted incidents without history)

#### Example API Requests:
```bash
# Get timeline for an incident (first 5 events, newest first)
curl "http://localhost:8000/incidents/3c240ff9-ee44-44ab-ba68-0a3ed92b9c06/timeline?page=1&page_size=5&sort_by=created_at&order=desc"

# Get specific page of timeline
curl "http://localhost:8000/incidents/3c240ff9-ee44-44ab-ba68-0a3ed92b9c06/timeline?page=2&page_size=20"
```

## Why Chronological Ordering Needs Deterministic Tie-Breaking

### The Problem:
When multiple events occur at the exact same timestamp, we need a deterministic way to order them.

### Why it Matters:
1. **Testing**: Tests need consistent results regardless of execution order
2. **Pagination**: Users should see the same events regardless of server load
3. **Debugging**: Audit trails should be reproducible
4. **APIs**: Consistent API responses are essential

### Solution:
- Primary sort by `created_at` timestamp
- Secondary sort by `id` (UUIDs are time-based but not guaranteed to be ordered)
- This ensures events with identical timestamps are ordered deterministically

### Example:
Two events created at the same second:
- Event 1: `created_at: "2026-10-16T12:30:00.000Z", id: "123..."
- Event 2: `created_at: "2026-10-16T12:30:00.000Z", id: "456..."

Ordering depends on UUID comparison, ensuring consistent results.

## How the Tests Use Temporary SQLite Databases

### Test Database Isolation:
- Each test uses a temporary SQLite database file
- Tests don't interfere with production data
- Tests can run in parallel without conflicts

### Setup Process:
```python
# In test_day7_timeline.py
def setup_test_database():
    test_db_path = tempfile.NamedTemporaryFile(suffix='_test.db', delete=False)
    test_db_path.close()

    # Create incident_events table with same structure as production
    conn = sqlite3.connect(test_db_path.name)
    cursor = conn.cursor()
    cursor.execute('''
        CREATE TABLE incident_events (
            id TEXT PRIMARY KEY,
            incident_id TEXT NOT NULL,
            event_type TEXT NOT NULL,
            description TEXT NOT NULL,
            old_values TEXT,
            new_values TEXT,
            created_at TEXT NOT NULL
        )
    ''')
    conn.commit()
    conn.close()

    # Configure app to use test database
    app.state.test_db_path = test_db_path.name
```

### Verification:
- Each test gets a fresh database
- Tests verify their own data without interference
- Database cleanup after each test run
- No shared state between tests
